# Разбор grep-ast и ast-grep (`meta10`)

## Назначение проекта

Репозиторий `meta10` содержит аналитический разбор и техническое исследование подходов к автоматическому извлечению (reverse engineering) описаний REST API-эндпоинтов и Kafka-событий непосредственно из исходного кода многоязычных микросервисов для генерации документации с помощью LLM-агентов.

На текущий момент проект представляет собой текстово-аналитическую базу знаний (без готовой библиотеки или исполняемого кода в ветке `main`), построенную вокруг критического анализа статьи Софьи Ермаковой (команда LLM-приложений ecom.tech) «Grep-AST или как мы заменили векторный поиск всего одной библиотекой» (Хабр, 3 марта 2026) и исследования исходного кода библиотеки `grep-ast` (версия `0.9.0`, автор Пол Готье).

## Архитектура и основные компоненты

Основной материал сосредоточен в файле [`review-habr-ecom-article.md`](review-habr-ecom-article.md) и охватывает следующие направления:

1. **Постановка задачи и сравнение подходов к поиску в коде**
   - Извлечение REST-эндпоинтов и Kafka-продюсеров/консьюмеров из сотен микросервисов на **5 языках**: Golang, Kotlin, Ruby, Elixir и PHP.
   - Разбор ограничений трёх базовых подходов:
     - **Tree-sitter напрямую** — распознаёт синтаксис (AST), но не семантику фреймворков, обёрток, DSL и макросов.
     - **RAG-пайплайн** (`gte-multilingual-base` + BM-25-реранкинг) — средняя точность около 85%, высокая задержка и непрозрачность отказов ретривера.
     - **Regex + grep** — хрупкость при изменении форматирования и ложные срабатывания в комментариях и строковых литералах.

2. **Внутренняя механика `grep-ast` (`0.9.0`)**
   - Разбор трёхфазной работы `TreeContext`:
     1. **Индексация AST (`walk_tree()`)** — парсинг через `tree-sitter` / `tree-sitter-language-pack` (100+ расширений файлов) и построение карты скоупов и заголовков многострочных узлов.
     2. **Текстовый поиск (`grep()`)** — обычный построчный `re.search()` без фильтрации по типу AST-узла.
     3. **Контекстуализация (`add_context()`)** — добавление родительских скоупов (`add_parent_scopes`), дочернего контекста (`add_child_context`), первых 3 строк файла (`margin`), ±1 строки вокруг совпадения (`LOI pad`), закрывающей строки блока и визуального форматирования (`│`, `█`, `⋮`).
   - Анализ обхода файлов `enumerate_files` (поддержка только ближайшего родительского `.gitignore`).

3. **Сравнение `grep-ast` vs `ast-grep` и интеграция с LLM-агентами**
   - Сопоставление инструментов: Python-библиотека `grep-ast` (CLI `grep-ast` / `gast`, regex + AST-контекст) против Rust-инструмента `ast-grep` (структурные AST-паттерны, YAML-правила, захват переменных, CLI / Node.js API / LSP).
   - Роль детерминированного поиска как `tool call` для итеративной навигации и трассируемости рассуждений LLM-агента (в контексте подходов Aider repo map, Claude Code и Cursor).

4. **Критический анализ и двухстадийный пайплайн `grep-ast → ast-grep → LLM`**
   - Выявлены 8 ключевых проблем оригинального подхода: отсутствие фильтрации ложных срабатываний на уровне AST в `grep-ast`, асимметрия метрик (85% для RAG без численной метрики для `grep-ast`), ложные отрицания при динамической генерации маршрутов (Rails `resources`, Elixir-макросы, конфигурируемые роуты в Go), нераскрытое управление паттернами и промптом агента, узкие места производительности (отсутствие параллелизма и кеширования AST, Python GIL, чтение файлов целиком), ограничения `.gitignore` и недооценка `ast-grep`.
   - Предложена трёхстадийная схема:
     - **Стадия 1 (`grep-ast`)**: широкий regex-поиск по всему репозиторию для быстрого отбора кандидатов и получения LLM-читаемого структурного контекста.
     - **Стадия 2 (`ast-grep`)**: структурная YAML-валидация на отфильтрованном списке файлов, отсеивание комментариев/строк и захват метапеременных (`$PATH`, `$HANDLER`, `$TEMPLATE`, `$TOPIC`) с примерами правил для Kotlin, Golang, PHP, Elixir и Kafka.
     - **Стадия 3 (LLM)**: синтез документации по проверенным координатам и контексту (с опциональным RAG как fallback для динамических маршрутов).
